# M2 — native integrations (0.5.0)

## Available

- AI dashboard: quotas, tokens, cache, trends, models, projects, activity and recent events.
- Today, 7-day, 30-day and all-time periods; compact and expanded details. A separate heatmap covers the last 13 weeks.
- AI Studio preset with layouts adapted to monitors, without automatically enabling connections or permissions.
- Codex: optional refresh of actual account limits through the existing CLI login and App Server, every 5 minutes. No conversations are started.
- Codex API value: estimates for the last eight queried chats, only when returned by the service. These do not represent a bill, the entire account or the charts’ reporting period.
- Live Codex activity from local logs, refreshed every 3 seconds and seeded from history for long-running chats. Work, waiting and completion events are tracked; after 5 minutes without confirmation, an active state is marked as needing verification (“Da verificare”).
- Claude: optional live event and status line connections. Installation and restoration preserve other settings and hooks. Limits and API value appear only when provided by Claude.
- Spotify: track, artist, album, artwork and previous/play-pause/next controls, including in the widget menu. Optional activation; macOS may request Automation permission.
- Application status and macOS thermal state; optional FPS reduction under load or in Low Power Mode.

## Data and limitations

Counters come from `~/.codex/sessions` and `~/.claude/projects`. The app does not retain conversation text or read credentials. Scans run every 30 seconds in a separate actor, using unchanged-file caches and chunked reads; lines larger than approximately 1 MB are skipped. Missing logs, different schemas or activity on other computers may make history incomplete.

Claude connections store derived summaries in Application Support. Claude API value sums cumulative values from connected sessions; it is not a bill or an exact daily spending measurement. Local charts stay on the Mac. Codex/Claude account connections and Spotify artwork use the network only when enabled. Artwork comes from allowed Spotify domains.

Live states describe observed events and cannot guarantee every process’s current state. Temperature in degrees is unavailable; the app uses the public macOS thermal classification.

Claude installation/restoration and status line forwarding were tested with temporary files without changing the user’s profile. Codex account access was tested with real limits; cost estimates were unavailable for that account.

Still requiring real-world testing: Claude events/status line, Spotify permission and playback, and launch at login. Mission Control, monitor disconnection/reconnection and sleep/wake were manually tested on three monitors before the rename.

## Automatic data refresh

Native FSEvents detect changes, new sessions and atomic replacement of Claude summaries. Events are coalesced over approximately 2 seconds; a running scan finishes before the next update. Periodic fallback checks remain: 3 seconds for live states and 30 seconds for counters. Freshness depends on the client writing data; initial scans of large histories may take longer. Disabling local reading also stops filesystem notifications. Codex account limits are still queried every 5 minutes.

## Claude desktop limits

When local reading is enabled, the app also reads `~/Library/Application Support/Claude/plan-usage-history.json`, when present, for schema versions 1 and 2. The most recent desktop or status line reading is shown with its source and date; the two accounts may differ. The desktop file provides no reset times, so these are marked unavailable. Readings older than 30 minutes are marked stale; windows older than their duration are omitted. Opus/Sonnet details are available in the expanded view. No credential access or additional network requests are introduced. If the internal format changes and is unsupported, it is ignored.

## Claude limits: passive reads only (build 31, superseded by build 33)

The interactive Claude Code `/usage` polling introduced in build 25 was removed after the user reported a new chat session every five minutes. Not submitting a model prompt does not make an interactive client launch free of session-history side effects. Automatic updates and manual refresh now only reread existing desktop history and status-line snapshots. The toggle, executable reader and diagnostic launch command were removed; old `claudeAccountEnabled` settings are ignored when imported.

The status-line bridge receives data from user-started sessions. The desktop file can stop updating when Claude desktop is inactive; expired or missing limits remain unavailable rather than triggering a new client. No existing Claude conversations are deleted.

## Spotify player modes (build 27)

The widget offers Compact and Expanded modes from Settings → Integrations → Spotify and the widget context menu. Expanded mode shows larger artwork, title/artist/album, shuffle, repeat and Spotify volume controls in 10-point steps. Transport controls remain available in Compact mode. Volume is Spotify’s application volume, not system output volume. Small widgets automatically fall back to Compact mode; very small frames retain an open-app button, while the context menu still provides controls. A 360 × 360 point widget is recommended.

Up to six named shortcuts can be added and removed in Settings. Supported links are Spotify playlist, album and track URLs/URIs, including localized shared URLs. Shortcuts open the item in Spotify without starting playback automatically. Only validated Spotify item URIs are opened; imported favorites also undergo validation. No Spotify Web API login is required. Artwork fetching and the existing macOS Automation permission remain as before.

Visible controls and desktop click handling share the same layout geometry. Explicit developer previews use isolated fixture models whose playback/launch actions are disabled; no user track is changed by those previews.

Build, resource/localization and M1/M2 checks passed. Geometry checks cover expanded, compact and tiny frames, six favorites and non-overlapping click targets. The installed client returned volume/shuffle/repeat in a read-only check. Expanded/compact/small fixture screenshots were inspected. Playback-changing controls and actual user playlist navigation still require interactive use; no music state was changed during verification.


## Spotify responsiveness (build 28)

Playback notifications now trigger a forced metadata refresh; the three-second periodic read remains a fallback, including when Spotify Connect does not emit local events. Widget transport/shuffle/repeat/volume clicks receive immediate predicted feedback, then reconcile with Spotify. Pending commands and event revisions prevent older reads from overwriting newer feedback. Metadata is published without waiting for cover downloads; artwork loads separately and is matched to the track before being attached. Failed artwork downloads are throttled rather than retried on every notification.

Transport controls use a centered strip. The volume progress line is aligned to the speaker icons, with the percentage below it. Buttons have hover backgrounds and borders in SwiftUI settings/editor views and through native non-key desktop mouse tracking. Hover state is transient and does not write preferences.

Fixture previews show centered controls and the hover appearance; geometry/state tests passed. A read-only real-client metadata query took 246 ms in one cold check. This is not a measured end-to-end click latency or a comparison benchmark against another app. Real pointer/command/event timing and Spotify Connect behavior remain user-verifiable.


## Spotify pause stabilization (build 29)

Playback notifications are now refresh triggers only: their potentially delayed state payload no longer directly overwrites the UI. Transport clicks send explicit `play` or `pause` according to the requested state, rather than another toggle. A short, bounded 1.5-second intent window holds the requested indicator while Spotify acknowledges it; subsequent authoritative reads reconcile normally. A different track or unavailable player cancels that protection. Failed commands clear it, and command serials prevent older failures/settlement tasks from overriding a newer click. Follow-up reads occur after 150 ms and at settlement end.

Regression tests cover out-of-order playing/paused samples after a pause, expiration of the intent window and a different track. These are deterministic state tests, not a live reproduction benchmark. The actual client was queried without changing playback; the physical button sequence remains user-verifiable.


## Claude terminal parsing (build 30, superseded by removal in build 31)

The native `/usage` reader now processes CRLF as two terminal controls. Swift treats that pair as one `Character`; the previous screen reconstruction could paint it into a cell, overlay subsequent rows and lose valid quota headings during redraws. This caused unavailable limits even with a working authenticated client. The change preserves independent carriage returns, line feeds and cursor updates.

A regression fixture covers CRLF quota output. M2 checks passed with native filesystem events available, and a read-only query against Claude Code 2.1.236 returned both current limits and reset dates. No model prompt or manual Claude desktop refresh is required for this path. The integration still depends on the first-party CLI's terminal format; future format changes can require parser updates.


Build 31 verification: release build, localization, native resource and M2 checks passed, including legacy settings import. The installed app uses the passive paths already covered by desktop/status-line fixtures. No prolonged session-history observation was performed.


## Structured Claude account limits (build 33)

The optional account reader uses Claude Code's newline-delimited control protocol: `initialize`, then `get_usage` with `skip_behaviors`. The client runs in print mode with `--no-session-persistence`, no tools, an empty strict MCP configuration, no user/project setting sources, and user hooks disabled. No user message or model prompt is sent. Claude manages its own authentication; Sorayura does not extract credentials. Organization-managed hooks may still be enforced by the client. Proxy/certificate settings and privacy opt-outs are carried through.

One request runs at a time, at most every five minutes automatically, with a 25-second read deadline, bounded output and child cleanup. Manual refresh uses the same protocol. Missing clients, unsupported control requests, authentication and stale responses are reported without falling back to an interactive session. The cache fetch timestamp is retained; old cache responses are rejected and previous valid readings keep their original date. Idle windows without a reset remain valid; malformed percentages and expired reset dates are rejected.

The new opt-in is `claudeControlEnabled`; the removed interactive `claudeAccountEnabled` preference cannot enable it. When enabled, the widget and animation use Claude Code account/status-line data instead of potentially different desktop account data. The protocol was identified in Vorssaint's public integration; this reader is implemented independently using the project's Foundation process/pipe approach, without copying GPL source.

The installed Claude Code 2.1.236 throttles cache timestamp writes to five minutes even after a successful request. Readings retain that conservative timestamp and accept up to 330 seconds of age (including scheduling margin), rather than falsely failing after 90 seconds. Older or future cache timestamps are rejected.

Validation: structured quota fixtures cover idle resets, fractional ISO timestamps, invalid percentages, expired windows and cache-age boundaries. Existing M2, localization and resource checks passed. Two consecutive real client reads returned limits without adding conversation JSONL files. Initial testing exposed the five-minute timestamp-write throttle; the overly strict 90-second guard was corrected before final delivery.

Build 33 was installed and normally launched. Its automatic account read returned both limits without error and without new conversation JSONL files during observation. Long-running polling and GUI history were not inspected.
